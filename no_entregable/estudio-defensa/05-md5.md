# `md5.c`: el MD5 implementado según el RFC 1321

## Para qué existe

Las firmas del TP son un MD5: el hash de un texto que incluye el secreto. La consigna prohíbe
usar bibliotecas externas, así que lo implementamos nosotros siguiendo el RFC 1321
(https://www.rfc-editor.org/rfc/rfc1321).

## Qué es un hash (lo que hay que poder explicar)

- Una **función de hash** toma un mensaje de cualquier largo y devuelve un resultado de largo
  fijo. MD5 devuelve **128 bits = 16 bytes**, que se escriben como **32 caracteres
  hexadecimales**.
- **Es determinística:** el mismo mensaje da siempre el mismo hash. Por eso el servidor puede
  recalcularlo y comparar.
- **Cambiar un solo bit del mensaje cambia todo el resultado** (efecto avalancha).
- **No se puede volver atrás:** a partir del hash no se puede obtener el mensaje. Por eso
  mandar `md5(... | secreto)` no revela el secreto.
- **MD5 hoy no es seguro para firmas:** se conocen formas de fabricar colisiones (dos
  mensajes con el mismo hash). Lo correcto hoy sería HMAC con SHA-256. Lo usamos porque lo
  pide la consigna.

## La idea del algoritmo en cuatro pasos

Antes de ir línea por línea, el mapa:

1. **Estado inicial:** cuatro números de 32 bits (A, B, C, D) con valores fijos del RFC.
2. **Bloques:** el mensaje se procesa en bloques de **64 bytes (512 bits)**. Cada bloque
   "mezcla" el estado con 64 operaciones.
3. **Padding:** el último pedazo del mensaje no suele llenar un bloque, así que se completa
   con un byte `0x80`, ceros y, al final, el largo del mensaje en bits.
4. **Salida:** cuando ya se procesaron todos los bloques, los cuatro números del estado
   (16 bytes) **son** el hash, y se escriben como 32 caracteres hexa.

Abajo está el archivo completo, en orden. Conviene leerlo con `src/md5.c` abierto al lado.

## El header: `md5.h`

```c
#ifndef MD5_H
#define MD5_H

/* MD5 implementado a mano segun el RFC 1321:
   https://www.rfc-editor.org/rfc/rfc1321 */

#define MD5_HEX_LEN 33   // 32 caracteres hex + '\0'

/* calcula el MD5 de los primeros 'len' bytes de 'mensaje' y lo escribe
   en 'salida' como 32 caracteres hexadecimales en minuscula + '\0'. */
void md5_hex(char *mensaje, int len, char *salida);

#endif
```

- **`#ifndef` / `#define` / `#endif`:** la guarda de inclusión, para que el header no se lea dos
  veces en el mismo `.c`.
- **`MD5_HEX_LEN 33`:** el tamaño del buffer de salida. El hash son 16 bytes y cada byte se
  escribe con 2 caracteres hexa: 32 caracteres, más el `'\0'`. Todos los que llaman a `md5_hex`
  declaran `char firma[MD5_HEX_LEN]`.
- **`md5_hex(mensaje, len, salida)`:** la **única función pública**. Recibe el largo aparte (y no
  usa `strlen` adentro) para poder hashear cualquier secuencia de bytes, aunque tuviera un `'\0'`
  en el medio. Devuelve `void` porque no puede fallar.
- No hicimos la versión con *init / update / final* de las bibliotecas, porque nuestros mensajes
  son cortos y entran enteros en memoria.

## Líneas 1 a 9: comentario e includes

```c
/* implementacion de MD5 segun el RFC 1321 (R. Rivest, abril 1992):
   https://www.rfc-editor.org/rfc/rfc1321
   La seccion 3 describe el algoritmo (padding, largo, estado inicial y las
   4 rondas) y la seccion A.5 trae los vectores de prueba de test_md5.c. */

#include <stdio.h>
#include <string.h>
#include <stdint.h>
#include "md5.h"
```

- El comentario dice de dónde sale cada parte: la **sección 3** del RFC describe el algoritmo y
  el **apéndice A.5** trae los resultados conocidos con los que lo probamos.
- **`<stdio.h>`**: `sprintf`, para escribir cada byte en hexa.
- **`<string.h>`**: `memset` y `memcpy`, para armar la cola del padding.
- **`<stdint.h>`**: los tipos de **tamaño exacto**: `uint8_t` (1 byte sin signo), `uint32_t`
  (4 bytes sin signo) y `uint64_t` (8 bytes sin signo). MD5 está definido sobre palabras de
  exactamente 32 bits, y con `int` o `long` el tamaño depende de la máquina.
- **¿Por qué *sin signo*?** Porque las sumas tienen que "dar la vuelta" (si pasan de 2³² − 1,
  vuelven a empezar desde 0, que es la suma módulo 2³² del RFC), y los desplazamientos a la
  derecha (`>>`) no pueden arrastrar un bit de signo. En C, eso solo está garantizado con tipos
  `unsigned`.
- **`"md5.h"`**: nuestro propio header, para que el compilador verifique que `md5_hex` coincide
  con lo declarado.

## Líneas 31 a 35: `rotar_izq`

```c
/* rota los bits de x hacia la izquierda c lugares (los que salen por
   la izquierda entran por la derecha) */
static uint32_t rotar_izq(uint32_t x, int c) {
    return (x << c) | (x >> (32 - c));
}
```

- C tiene desplazamiento (`<<`, `>>`) pero no **rotación**, así que la armamos:
  - **`x << c`** corre los bits `c` lugares a la izquierda; los `c` de más a la izquierda se
    pierden y entran ceros por la derecha.
  - **`x >> (32 - c)`** se queda justamente con esos `c` bits que se perdieron, corridos hasta la
    derecha.
  - **`|`** (OR bit a bit) junta las dos partes.
- Ejemplo con 8 bits para que se vea: rotar `1011 0001` 3 lugares da `1000 1101`.
- Es `static` porque es una función auxiliar interna, solo para este archivo.

## Líneas 37 a 84: `procesar_bloque`, el corazón de MD5

Procesa **un bloque de 64 bytes** y actualiza el estado. Se llama una vez por bloque.

### Líneas 37 a 39: parámetros y variables

```c
static void procesar_bloque(uint32_t *estado, uint8_t *bloque) {
    uint32_t M[16]; // bloque visto como 16 palabras de 32 bits
    int i;
```

- **`estado`**: un puntero a los 4 números A, B, C, D. Como es un puntero, la función **modifica
  el estado de quien la llamó** (no una copia).
- **`bloque`**: un puntero a los 64 bytes a procesar.
- **`M[16]`**: el mismo bloque, pero visto como 16 palabras de 32 bits (16 × 4 = 64 bytes).

### Líneas 41 a 47: de 64 bytes a 16 palabras

```c
    // armamos cada palabra con 4 bytes en little-endian
    for (i = 0; i < 16; i++) {
        M[i] = (uint32_t) bloque[i*4]
            | ((uint32_t) bloque[i*4 + 1] << 8)
            | ((uint32_t) bloque[i*4 + 2] << 16)
            | ((uint32_t) bloque[i*4 + 3] << 24);
    }
```

- Cada palabra `M[i]` se arma con 4 bytes seguidos del bloque: `bloque[i*4]` a `bloque[i*4+3]`.
- **Little-endian:** el RFC dice que el **primer byte es el menos significativo**. Por eso el
  primero va sin correr, el segundo corrido 8 bits, el tercero 16 y el cuarto 24, y se juntan con
  `|`. Ejemplo: los bytes `61 62 63 80` (`"abc"` + `0x80`) forman la palabra `0x80636261`.
- **`(uint32_t)`** convierte cada byte a 32 bits **antes** de correrlo. Sin la conversión, el
  byte se correría como un `int` con signo y `<< 24` podría dar un resultado incorrecto.
- Lo hacemos a mano en vez de copiar los bytes con `memcpy` para que funcione igual en cualquier
  máquina, sea little-endian o big-endian.

### Líneas 49 a 54: copiar el estado

```c
    uint32_t A = estado[0];
    uint32_t B = estado[1];
    uint32_t C = estado[2];
    uint32_t D = estado[3];
    uint32_t F, temp;
    int g;
```

- **A, B, C, D**: copias del estado. Las 64 operaciones trabajan sobre estas copias, y recién al
  final se suman al estado.
- **`F`**: el resultado de la función lógica de cada paso.
- **`temp`**: una variable auxiliar para el "enroque" de las cuatro variables.
- **`g`**: qué palabra del bloque (`M[g]`) se usa en cada paso.

### Líneas 56 a 70: las 4 rondas

```c
    // 64 pasos en 4 rondas de 16
    for (i = 0; i < 64; i++) {
        if (i < 16) {             // ronda 1
            F = (B & C) | (~B & D);
            g = i;
        } else if (i < 32) {      // ronda 2
            F = (D & B) | (~D & C);
            g = (5*i + 1) % 16;
        } else if (i < 48) {      // ronda 3
            F = B ^ C ^ D;
            g = (3*i + 5) % 16;
        } else {                  // ronda 4
            F = C ^ (B | ~D);
            g = (7*i) % 16;
        }
```

- **64 pasos en 4 rondas de 16.** Cada ronda usa una **función lógica distinta** (en el RFC se
  llaman F, G, H e I) que mezcla B, C y D **bit a bit**. Los operadores: `&` es AND, `|` es OR,
  `^` es XOR y `~` es NOT (invierte todos los bits).
  - **Ronda 1:** `(B & C) | (~B & D)` = "si el bit de B es 1, tomá el de C; si es 0, el de D".
  - **Ronda 2:** lo mismo pero eligiendo con D.
  - **Ronda 3:** el XOR de los tres.
  - **Ronda 4:** `C ^ (B | ~D)`.
- **`g`** elige qué palabra del bloque entra en cada paso, y cada ronda las recorre en un orden
  distinto:
  - ronda 1: en orden, 0, 1, 2, …, 15;
  - ronda 2: `(5i + 1) % 16` = 1, 6, 11, 0, …;
  - ronda 3: `(3i + 5) % 16`;
  - ronda 4: `(7i) % 16`.
  El `% 16` (resto de dividir por 16) hace que el índice siempre caiga entre 0 y 15. Así, cada
  palabra del bloque participa una vez por ronda, cuatro en total.

### Líneas 72 a 77: un paso

```c
        temp = D;
        D = C;
        C = B;
        B = B + rotar_izq(A + F + K[i] + M[g], S[i]);
        A = temp;
    }
```

Esta es **la operación del RFC**, escrita como "enroque":

1. Se guarda D en `temp`.
2. D toma el valor de C, y C el de B (las variables se corren un lugar).
3. **El B nuevo** es el B de antes más una rotación de la suma de cuatro cosas: **A**, el
   resultado de la función lógica **F**, la constante del paso **`K[i]`** y la palabra del bloque
   **`M[g]`**. La rotación es de **`S[i]`** bits.
4. A toma el valor que tenía D (guardado en `temp`).

Las sumas son de `uint32_t`, así que se hacen **módulo 2³²** solas: si se pasan, dan la vuelta.
Después de cada paso, el valor nuevo queda en B y los otros tres "rotan" de lugar.

### Líneas 79 a 84: sumar al estado

```c
    // sumamos el resultado del bloque al estado
    estado[0] += A;
    estado[1] += B;
    estado[2] += C;
    estado[3] += D;
}
```

- El resultado del bloque **se suma** al estado (no lo reemplaza). Así, el estado después del
  último bloque depende de **todos** los bloques del mensaje.
- Como `estado` es un puntero, estos cambios quedan en la variable de `md5_hex`.

## Líneas 86 a 127: `md5_hex`, la función pública

### Líneas 86 a 96: las variables

```c
void md5_hex(char *mensaje, int len, char *salida) {
    uint8_t *datos = (uint8_t *) mensaje; // castear mensaje a bytes sin signo
    int bloques_completos = len/64; // bloques que no necesitan padding
    int resto = len % 64; // bytes que si necesitan padding
    uint8_t cola[128]; // resto más padding (a lo sumo 2 bloques)

    int cola_len;
    uint64_t largo_bits = (uint64_t) len * 8;
    uint32_t estado[4] = {0x67452301, 0xefcdab89, 0x98badcfe, 0x10325476}; // A,B,C,D fijos sacados del RFC
    uint8_t byte;
    int i;
```

- **`datos`**: el mismo mensaje, pero visto como **bytes sin signo**. El *cast*
  `(uint8_t *) mensaje` no copia nada: solo cambia cómo se interpretan los mismos bytes. Hace
  falta porque `char` puede tener signo, y un byte como `0xE2` se leería como negativo.
- **`bloques_completos = len / 64`**: cuántos bloques de 64 bytes entran enteros (división
  entera: 100 / 64 = 1).
- **`resto = len % 64`**: cuántos bytes sobran después de esos bloques (100 % 64 = 36).
- **`cola[128]`**: dónde armamos el último pedazo con el padding. Son 128 bytes porque a veces
  hacen falta **dos** bloques (ver más abajo).
- **`cola_len`**: cuántos bytes de la cola se usan, 64 o 128.
- **`largo_bits`**: el largo del mensaje **en bits** (bytes × 8), que va al final del padding. Es
  de 64 bits porque el RFC reserva 8 bytes para él. El `(uint64_t)` convierte `len` **antes** de
  multiplicar, para que la cuenta se haga en 64 bits.
- **`estado[4]`**: el **estado inicial** A, B, C, D. Son valores fijos que da el RFC (en memoria,
  los bytes son `01 23 45 67 89 ab cd ef fe dc ba 98 76 54 32 10`).
- **`byte`**: el byte que vamos a escribir en hexa al final.

### Líneas 98 a 100: los bloques completos

```c
    // procesamos los bloques completos directamente desde el mensaje
    for (i = 0; i < bloques_completos; i++)
        procesar_bloque(estado, datos + i*64);
```

- Los bloques que están completos no necesitan nada más: se procesan **directo desde el
  mensaje**, sin copiarlos.
- **`datos + i*64`**: la dirección del bloque número `i` (aritmética de punteros: avanzar
  `i*64` bytes).
- En nuestro TP los mensajes son cortos (el pedido firmado tiene unos 40 bytes), así que casi
  siempre `bloques_completos` es 0 y todo se procesa en la cola. Los vectores de prueba del RFC
  sí tienen mensajes de más de 64 bytes.

### Líneas 102 a 105: empezar la cola

```c
    // copiamos los bytes que sobran y agregamos el bit 1 (byte 0x80)
    memset(cola, 0, sizeof(cola)); // limpiamos la cola
    memcpy(cola, datos + bloques_completos * 64, resto); // copiar bytes del bloque incompleto a la cola
    cola[resto] = 0x80;
```

- **`memset(cola, 0, ...)`**: los 128 bytes en cero. Así, el relleno con ceros que pide el RFC ya
  está hecho.
- **`memcpy(cola, datos + bloques_completos * 64, resto)`**: copia los `resto` bytes que
  sobraron (los que están después del último bloque completo) al principio de la cola.
- **`cola[resto] = 0x80`**: justo después de los datos, el byte `0x80` = `1000 0000` en binario.
  Es "un bit 1 seguido de ceros", que el RFC agrega siempre, incluso si el mensaje llenaba
  justo un bloque. Marca dónde termina el mensaje.

### Líneas 107 a 111: ¿uno o dos bloques?

```c
    // si entran los 8 bytes del largo usamos un bloque, sino 2
    if (resto < 56)
        cola_len = 64;
    else
        cola_len = 128;
```

- Al final hay que poner el largo (8 bytes). En un bloque de 64 bytes, el largo ocupa los bytes
  56 a 63, así que los datos más el `0x80` tienen que terminar antes del byte 56.
- **Si `resto < 56`**: los datos (`resto` bytes) + el `0x80` (1 byte) + el largo (8 bytes)
  entran en 64 → **un bloque**.
- **Si `resto >= 56`**: no entran, y hace falta **un segundo bloque**, casi todo de ceros, con el
  largo al final → **128 bytes**. Uno de los vectores de prueba (62 caracteres) cae justo en
  este caso.

### Líneas 113 a 115: el largo al final

```c
    // ponemos el largo en bits en little endian en los últimos 8 bytes
    for (i = 0; i < 8; i++)
        cola[cola_len - 8 + i] = (largo_bits >> (8*i)) & 0xff;
```

- Escribe los 8 bytes de `largo_bits` en los **últimos 8 lugares** de la cola
  (`cola_len - 8` a `cola_len - 1`).
- **`(largo_bits >> (8*i)) & 0xff`** saca el byte número `i`: corre el número `8*i` bits a la
  derecha y se queda con los 8 bits de abajo (`& 0xff` = AND con `1111 1111`).
- Con `i = 0` sale el byte **menos significativo**, que va primero: es **little-endian**, como
  pide el RFC.
- Ejemplo: `"abc"` son 3 bytes = 24 bits = `0x18`. La cola queda
  `61 62 63 80 00 … 00 18 00 00 00 00 00 00 00`.
- **Un error que tuvimos acá:** escribimos `+1` donde iba `+i`. El compilador no lo detecta y el
  hash sale completamente distinto. Lo encontramos imprimiendo los bytes de la cola y
  comparándolos con el ejemplo de arriba.

### Líneas 117 a 119: procesar la cola

```c
    // procesamos la cola (1 o 2 bloques)
    for (i = 0; i < cola_len; i += 64)
        procesar_bloque(estado, cola + i);
```

- Recorre la cola de a 64 bytes: una vuelta si `cola_len` es 64 y dos si es 128.
- **`i += 64`**: el contador avanza de a un bloque.

### Líneas 121 a 127: escribir el resultado en hexa

```c
    /* salida: el estado son 16 bytes (A, B, C, D en little-endian).
       Cada byte se escribe como 2 caracteres hex en minuscula. */
    for (i = 0; i < 16; i++) {
        byte = (estado[i / 4] >> (8 * (i % 4))) & 0xff;
        sprintf(salida + i*2, "%02x", byte);
    }
}
```

- El hash son los 4 números del estado, o sea **16 bytes**. El loop los recorre uno por uno.
- **`estado[i / 4]`**: los bytes 0–3 salen de A, 4–7 de B, 8–11 de C y 12–15 de D (división
  entera).
- **`>> (8 * (i % 4)) & 0xff`**: saca el byte número `i % 4` de esa palabra, empezando por el
  menos significativo (little-endian otra vez, como pide el RFC).
- **`sprintf(salida + i*2, "%02x", byte)`** escribe el byte como texto en la posición `i*2` de la
  salida (cada byte ocupa 2 caracteres):
  - **`%x`**: hexadecimal en minúscula.
  - **`02`**: siempre 2 dígitos, rellenando con un cero adelante (`0a`, no `a`).
- `sprintf` agrega un `'\0'` después de cada escritura; el de la última vuelta queda en la
  posición 32 y termina el string. Por eso `salida` necesita 33 lugares (`MD5_HEX_LEN`).

## Cómo sabemos que está bien

`test_md5.c` compara contra resultados conocidos (ver `09-tests-y-makefile.md`):

- 4 vectores del RFC 1321, apéndice A.5: `""` → `d41d8cd98f00b204e9800998ecf8427e`, `"abc"`, un
  texto de 80 dígitos (más de un bloque) y uno de 62 caracteres (resto ≥ 56: la cola ocupa 2
  bloques).
- Los dos ejemplos del enunciado: `grupo01|180.11.1.3|secreto01` →
  `f21d11f08cf40377860fd75d8bfd73cb` y `200|Port|17189|secreto01` →
  `6d720e86a353852c268b2071dffaf069`.

Resultado: 6 de 6. Además, la autenticación contra el servidor real dio 200, así que el
servidor aceptó nuestras firmas.

## Preguntas que pueden hacer sobre este archivo

| Pregunta | Respuesta corta |
|---|---|
| ¿Qué devuelve MD5? | 128 bits = 16 bytes, escritos como 32 caracteres hexa |
| ¿Por qué `uint32_t` y no `int`? | MD5 usa palabras de exactamente 32 bits sin signo: las sumas dan la vuelta módulo 2³² y los `>>` no arrastran signo |
| ¿De qué tamaño son los bloques? | 64 bytes (512 bits) |
| ¿Qué es el padding? | Un byte `0x80`, ceros y el largo del mensaje en bits en los últimos 8 bytes |
| ¿Cuándo hacen falta 2 bloques de cola? | Cuando sobran 56 bytes o más: no entran el `0x80` y los 8 bytes del largo |
| ¿Qué es little-endian? | El byte menos significativo va primero; MD5 lo usa para las palabras, el largo y la salida |
| ¿Qué son `K` y `S`? | Constantes del RFC: `K` se suma en cada paso y `S` dice cuántos bits rotar |
| ¿Por qué el cast a `uint8_t *`? | Para leer los bytes sin signo: un `char` con signo haría negativos los bytes ≥ `0x80` |
| ¿Por qué `md5_hex` recibe el largo? | Para no depender de `strlen` y poder hashear cualquier secuencia de bytes |
| ¿Es seguro MD5? | No para firmas (hay colisiones); lo correcto hoy sería HMAC-SHA-256, pero lo pide la consigna |
