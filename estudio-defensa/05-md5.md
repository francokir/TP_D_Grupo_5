# `md5.c`: el MD5 implementado según el RFC 1321

## Para qué existe

Las firmas del TP son un MD5: el hash de un texto que incluye el secreto. La consigna prohíbe
usar bibliotecas externas, así que lo implementamos nosotros siguiendo el RFC 1321.

## Qué es un hash (lo que hay que poder explicar)

- Una **función de hash** toma un mensaje de cualquier largo y devuelve un resultado de largo
  fijo. MD5 devuelve **128 bits = 16 bytes**, que se escriben como **32 caracteres
  hexadecimales**.
- **Es determinística:** el mismo mensaje da siempre el mismo hash. Por eso el servidor puede
  recalcularlo y comparar.
- **Cambiar un solo bit del mensaje cambia todo el resultado** (efecto avalancha).
- **No se puede volver atrás:** a partir del hash no se puede obtener el mensaje. Por eso
  mandar `md5(... | secreto)` no revela el secreto.
- **MD5 hoy no es seguro para firmas:** se conocen formas de fabricar colisiones (dos
  mensajes con el mismo hash). Lo correcto hoy sería HMAC con SHA-256. Lo usamos porque lo
  pide la consigna.

## La interfaz (`md5.h`)

```c
#define MD5_HEX_LEN 33   // 32 caracteres hex + '\0'
void md5_hex(char *mensaje, int len, char *salida);
```

Una sola función pública: recibe `len` bytes de `mensaje` y escribe en `salida` los 32
caracteres hexa en minúscula más el `'\0'`. Quien llama tiene que pasar un buffer de
`MD5_HEX_LEN`. No hicimos la versión init/update/final porque nuestros mensajes son cortos y
caben enteros en memoria.

## Cómo funciona, en cuatro pasos

### Paso 1: el estado inicial

```c
uint32_t estado[4] = {0x67452301, 0xefcdab89, 0x98badcfe, 0x10325476}; // A, B, C, D
```

Son cuatro palabras de 32 bits con valores fijos que da el RFC. Cada bloque del mensaje las va
modificando, y al final esas cuatro palabras **son** el hash.

Usamos `uint32_t` y `uint8_t` (de `stdint.h`) porque necesitamos exactamente 32 bits sin signo:
las sumas tienen que "dar la vuelta" módulo 2³², y los desplazamientos no pueden arrastrar el
signo.

### Paso 2: procesar los bloques completos

MD5 trabaja en **bloques de 64 bytes (512 bits)**.

```c
int bloques_completos = len / 64;
for (i = 0; i < bloques_completos; i++)
    procesar_bloque(estado, datos + i*64);
```

Los bloques que están completos se procesan directo desde el mensaje.

### Paso 3: el padding (la "cola")

Lo que sobra (`resto = len % 64` bytes) no completa un bloque, así que se rellena:

```c
memset(cola, 0, sizeof(cola));                        // 128 bytes en cero
memcpy(cola, datos + bloques_completos * 64, resto);  // los bytes que sobraron
cola[resto] = 0x80;                                   // un bit 1 (0x80 = 1000 0000)
cola_len = (resto < 56) ? 64 : 128;                   // ¿entra el largo en este bloque?
for (i = 0; i < 8; i++)                                // largo en bits, little-endian
    cola[cola_len - 8 + i] = (largo_bits >> (8*i)) & 0xff;
```

1. Se copian los bytes que sobraron.
2. Se agrega el byte **`0x80`**, que es un bit 1 seguido de ceros.
3. Se rellena con ceros.
4. Los **últimos 8 bytes** guardan el **largo del mensaje original en bits**, en
   **little-endian** (el byte menos significativo primero).

¿Por qué a veces 2 bloques? Al resto hay que sumarle el `0x80` (1 byte) y el largo (8 bytes).
Si el resto es de 56 bytes o más, `resto + 1 + 8 > 64` y no entra: hace falta un segundo
bloque. Por eso `cola` tiene 128 bytes.

Ejemplo: `"abc"` son 3 bytes → cola de 64 bytes = `61 62 63 80 00 … 00 18 00 00 00 00 00 00 00`
(`0x18` = 24 bits).

### Paso 4: `procesar_bloque`, las 64 operaciones

```c
// 1) los 64 bytes del bloque se leen como 16 palabras de 32 bits, en little-endian
M[i] = bloque[i*4] | (bloque[i*4+1] << 8) | (bloque[i*4+2] << 16) | (bloque[i*4+3] << 24);

// 2) 64 pasos en 4 rondas de 16
for (i = 0; i < 64; i++) {
    if      (i < 16) { F = (B & C) | (~B & D); g = i; }               // ronda 1
    else if (i < 32) { F = (D & B) | (~D & C); g = (5*i + 1) % 16; }  // ronda 2
    else if (i < 48) { F = B ^ C ^ D;          g = (3*i + 5) % 16; }  // ronda 3
    else             { F = C ^ (B | ~D);       g = (7*i) % 16; }      // ronda 4
    temp = D; D = C; C = B;
    B = B + rotar_izq(A + F + K[i] + M[g], S[i]);
    A = temp;
}

// 3) se suma el resultado al estado
estado[0] += A; estado[1] += B; estado[2] += C; estado[3] += D;
```

- Cada ronda usa una **función lógica distinta** (F, G, H, I en el RFC) que mezcla B, C y D
  bit a bit.
- `g` dice **qué palabra del bloque** se usa en cada paso; cada ronda las recorre en otro orden.
- **`K[64]`** son constantes del RFC: la parte entera de |sen(i+1)| × 2³².
- **`S[64]`** dice cuántos bits rotar en cada paso.
- `rotar_izq(x, c)` = `(x << c) | (x >> (32 - c))`: los bits que salen por la izquierda
  vuelven a entrar por la derecha.
- Después de cada paso las cuatro variables "rotan" de lugar (A ← D, D ← C, C ← B, y B es el
  valor nuevo).

### Salida: de 16 bytes a 32 caracteres

```c
for (i = 0; i < 16; i++) {
    byte = (estado[i / 4] >> (8 * (i % 4))) & 0xff;  // A, B, C, D en little-endian
    sprintf(salida + i*2, "%02x", byte);              // 2 caracteres hexa por byte
}
```

`%02x` escribe el byte en hexadecimal minúscula, siempre con dos dígitos (`0a`, no `a`). El
último `sprintf` deja el `'\0'` al final.

## Cómo sabemos que está bien

`test_md5.c` compara contra:

- 4 vectores del RFC 1321: `""` → `d41d8cd98f00b204e9800998ecf8427e`, `"abc"`, un texto de 80
  dígitos (más de un bloque) y uno de 62 caracteres (resto ≥ 56: la cola ocupa 2 bloques).
- Los dos ejemplos del enunciado: `grupo01|180.11.1.3|secreto01` →
  `f21d11f08cf40377860fd75d8bfd73cb` y `200|Port|17189|secreto01` →
  `6d720e86a353852c268b2071dffaf069`.

Resultado: 6 de 6. Además, la autenticación contra el servidor real dio 200, así que el
servidor aceptó nuestras firmas.

Un error que tuvimos: en el padding escribimos `+1` donde iba `+i`. El compilador no lo detecta
y el hash sale completamente distinto. Lo encontramos imprimiendo los bytes de la cola y
comparándolos con lo esperado.
